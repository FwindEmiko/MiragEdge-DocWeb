# 验证与实服验收

附魔配置通过 YAML 解析或 `/aiyatsbus reload`，只说明问题没有在那个阶段暴露。上线前需要把验证分成四层，每层的结论都要单独记录。

## 第一层：静态检查

检查范围：YAML 语法、缩进、重复 ID、变量名一致性、脚本中明显错误的函数名和参数数。

| 检查项 | 通过标准 |
| --- | --- |
| YAML | 所有待部署文件可被 YAML 工具解析，块标量缩进正确 |
| ID | 与同一 Aiyatsbus 配置集和数据包登记表不重复 |
| 显示 | `display` 中引用的变量在 `variables` 中存在 |
| 脚本 | `modifiable` 使用函数读写，`&event` 只出现在监听器中 |
| API | 每个新增 `::` 调用可在当前 Fluxon 扩展或上游默认配置找到依据 |

静态通过不能证明插件会加载，也不能证明 Bukkit 事件会按预期触发。

## 第二层：加载检查

1. 将配置部署到测试服对应的 `plugins/Aiyatsbus/enchants/` 目录。
2. 执行 `/aiyatsbus reload`。
3. 保存完整控制台输出，重点看 YAML 解析、脚本预热和注册相关异常。
4. 用 `/aiyatsbus book <enchant> [level] [player]` 确认可以生成书本。
5. 用 `/aiyatsbus enchant <enchant> [level] [player]` 确认主手物品能获得目标等级。

通过条件是没有相关加载错误，并且书本/主手附魔的注册结果符合预期。它仍不证明游戏内效果正确。

## 第三层：功能测试

每个附魔至少覆盖以下维度：

| 维度 | 要测内容 |
| --- | --- |
| 目标 | 正确物品可附魔，错误物品和错误槽位不会触发 |
| 等级 | 最低、常用、最高等级的数值和展示一致 |
| 事件 | 正确动作触发，错误动作和空气点击不触发 |
| 冷却 | 首次、冷却中、冷却结束三种状态正确 |
| 状态 | `modifiable` 在重复触发、换手、重登后的表现符合设计 |
| 边界 | 死亡、掉落、拾取、换甲、创造模式和旁观模式按设计处理 |
| 保护 | PVP、领地、世界禁用列表和反作弊不会产生绕过或误伤 |

对伤害、位移、挖掘、爆炸和药水效果，记录测试前后数值，不要只凭肉眼判断“好像生效”。

## 第四层：组合回归

涉及数据包、原版替代或其他装备系统时，按 [数据包边界](./datapack-boundaries) 的四组合表测试。还要检查：

- 同类附魔冲突限制是否仍有效。
- 多件装备同时佩戴时是否重复执行。
- 多名玩家同时触发 ticker 时是否有状态串扰或性能异常。
- 服务端重载和玩家重新登录后是否保留了不该保留的状态。

## 验收记录模板

```text
附魔 ID:
测试版本: Aiyatsbus / 服务端 / 数据包版本
测试人:
日期:

静态检查: 通过 / 未通过
reload: 通过 / 未通过（日志位置）
书本与主手附魔: 通过 / 未通过
功能场景: 列出已测等级、物品、动作和结果
数据包四组合: 列出四种开关组合与结果
区域保护/反作弊: 已测范围与结果
结论: 仅静态通过 / 测试服通过 / 实服验收通过
```

没有游戏内记录时，结论最多写“静态检查通过”或“reload 通过”。不要把源码推断、YAML 检查或测试服单场景结果写成正式服长期行为。
